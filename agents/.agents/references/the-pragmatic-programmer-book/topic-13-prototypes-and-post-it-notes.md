## Topic 13: Prototypes and Post-it Notes

Prototyping exposes risk and answers specific questions about a system at low cost before full development. Prototypes do not require production code; teams can use Post-it notes, whiteboard drawings, or high-level scripting languages to test workflows, architectures, and interfaces. The main value of a prototype lies in the lessons learned rather than the code produced.

### The Pragmatic Approach

- **Prototype to learn**: Target specific risks, unproven ideas, architecture, performance limits, or third-party tools.
- **Ignore production details**: Omit error handling, complete data validation, coding style, and exhaustive documentation to accelerate feedback.
- **Use lightweight tools**: Build mockups with paper, whiteboards, or high-level languages to keep prototyping fast and non-restrictive.
- **Test architecture early**: Verify component responsibilities, coupling, and data access paths without writing full module logic.

### Common Mistakes

- **Treating prototype code as production code**: Failing to communicate that prototype code is disposable leads stakeholders to deploy incomplete software.
- **Fixating on unnecessary details**: Spending time on full correctness, robustness, or UI polish defeats the goal of fast learning.
- **Confusing prototypes with functional systems**: Attempting to complete a prototype instead of discarding it creates fragile technical debt.
