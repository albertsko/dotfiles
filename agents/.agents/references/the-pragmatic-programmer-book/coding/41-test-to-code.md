## 41. Test to Code

Testing is a design and feedback activity whose greatest value comes from thinking about and writing tests, not merely running them to find bugs. Treat a test as the code's first user: it forces engineers to clarify a unit's contract, boundary conditions, error behavior, dependencies, and public interface; difficult setup exposes coupling, while explicit parameters and controlled dependencies produce flexible, observable components. Use short test-driven development cycles when useful, but guide them toward small end-to-end behavior and customer feedback so passing tests advance the actual solution instead of rewarding local polish. Test each unit against its contract, preserve every discovered failure as a regression test, reuse test facilities as units are assembled, expose safe diagnostics for deployed code, and maintain tests as carefully as production code. Tests also communicate expected behavior to other developers, and a healthy testing culture keeps the suite passing continuously because testing, design, and coding form one engineering activity.

### The Pragmatic Approach

- Define each unit's contract before implementing it: state accepted inputs, rejected inputs, promised results, boundary behavior, and error behavior. Use tests to confirm both that the code honors the contract and that the contract expresses the intended behavior.
- Design from the caller's perspective by writing or imagining the first test before the implementation. Pass controllable dependencies and unresolved policy choices as parameters instead of reading global state or hard-coding an ambiguous decision.
- Make dependencies replaceable and internal state observable through explicit interfaces. Treat extensive test setup as evidence that the unit has excessive coupling.
- Build small end-to-end slices that deliver observable behavior, then use what you learn and customer feedback to choose the next slice.
- Keep each test-driven development cycle to minutes: select one behavior, write a test, run the full suite to verify that only the new test fails for the expected reason, implement the smallest useful change, rerun the suite, and refactor while it stays green.
- Maintain a destination beyond the next passing test. Reassess whether each cycle advances the real solution, especially when representation details or easy cases consume repeated effort.
- Test units in isolation under controlled conditions and in dependency order. Verify each dependency's full contract first, then test the consuming unit's contract and its use of those dependencies. If the dependency tests pass while the consumer fails, focus debugging on the consumer or its use of those dependencies. Reuse the unit test facilities when testing the assembled system.
- Derive cases from the contract rather than random examples. Cover valid ranges, boundary values, invalid inputs, promised outputs, and failures; for a square-root function, test zero, representative positive and large values, acceptable numerical error, and rejection of negatives.
- Convert every useful console experiment, debugger probe, or manual reproduction into an automated regression test after debugging.
- Provide a safe production test window that exposes internal state without a debugger. Use consistent, machine-parseable logs and controlled diagnostic switches for selected users or user groups.
- Test stable behavior instead of incidental details such as widget coordinates, exact timestamps, or error-message wording. Keep test code clean, decoupled, deterministic, robust, and maintainable.
- Keep all tests passing. Fix or remove tests that always fail, delete redundant tests, and favor meaningful behavior over chasing 100% coverage.
- Use tests to communicate expected behavior, especially for shared code and code that relies on peculiar external dependencies.
- Plan to test software thoroughly before users become its testers. Test first when practical and test during implementation when necessary. Never defer testing to an unspecified later phase.
