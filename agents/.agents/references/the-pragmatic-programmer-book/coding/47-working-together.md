## 47. Working Together

Work with developers and extended team members such as users, testers, sponsors, and domain experts while writing code, so the team can resolve requirements, design choices, and defects through immediate discussion, live code, and demos instead of relying on endless meetings, memos, or excessive documentation. In pair programming, one developer types while both developers solve the problem; mob programming applies the same tight, live-coding collaboration to a larger, diverse group, and the non-typing collaborators can focus on broader design, scope, and quality. Because software tends to mirror its team's communication paths, structure collaboration around the architecture and user involvement you want the system to exhibit.

### The Pragmatic Approach

- Try pair programming for a few hours at a time over at least two weeks before judging it, because the workflow takes time to become natural.
- Share responsibility for the solution: let one developer type while both developers reason about the problem, and switch typing duties as needed.
- Use the non-typing partner's attention to examine higher-level design and scope while the typist handles syntax and implementation details.
- Draw on collaborators' different backgrounds, experience, problem-solving techniques, and levels of focus to broaden the solution and challenge assumptions.
- Treat peer accountability as a quality control that discourages weak naming, bad habits, and embarrassing shortcuts.
- Form a mob of four or five people to brainstorm new ideas or diagnose a difficult problem, and rotate the typist every five to ten minutes.
- Include people who can resolve uncertainty, such as users, testers, sponsors, and domain experts, in live coding sessions instead of limiting collaboration to developers.
- Treat co-located, remote, solo, pair, and mob programming as viable working styles, and experiment with a different style when the team has used only one.
- Learn the rules, advantages, and pitfalls of an unfamiliar collaboration style from both practical experience reports and technical guidance before adopting it.
- Start with short sessions and simple exercises before applying an unfamiliar collaboration style to difficult production code.
- Critique the code rather than the person. Say, “Let's inspect this block and its assumptions,” instead of, “You're wrong.”
- Build the code, not your ego: listen to competing viewpoints, try to understand them, and optimize for code quality rather than personal credit.
- Run frequent retrospectives and apply what you learn to improve the next pairing or mobbing session.
- Shape team communication around the architecture you want, and include users in the development team when you want the software to reflect their needs.
