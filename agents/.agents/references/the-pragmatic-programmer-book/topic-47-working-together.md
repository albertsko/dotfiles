## Topic 47: Working Together

Development is most effective when developers, users, testers, and stakeholders collaborate directly during live coding rather than relying on heavy documentation and formal meetings. Conway's Law demonstrates that software designs naturally copy organizational communication structures. Team members can deliberately organize their structure to shape the resulting software architecture and ensure user needs shape the final product. Pair programming pairs a typist focusing on low-level syntax with an observer focusing on high-level strategy, which reduces mistakes and improves code quality. Mob programming expands live collaboration to larger group sessions involving cross-functional team members.

### The Pragmatic Approach

- Program collaboratively using pair or mob programming sessions to solve complex problems in real time.
- Include non-developer stakeholders such as users, testers, and project sponsors directly in live coding and discussion sessions.
- Swap typist roles frequently during mob programming sessions every 5 to 10 minutes.
- Focus on the code rather than personal egos, and critique code constructions instead of individual developers.
- Conduct regular retrospectives to analyze collaborative habits and refine team dynamics.

### Common Mistakes

- Relying on heavy, exhaustive documentation and formal meetings instead of continuous, live collaboration.
- Working in isolated silos that cause software components to become disconnected and stove-piped.
- Restricting pairing and mobbing strictly to software developers while excluding users and domain experts.
- Letting personal ego drive technical debates or attacking individual developers instead of evaluating the code.
- Trying pair or mob programming without structured rules, reasonable time limits, or small initial test sessions.
