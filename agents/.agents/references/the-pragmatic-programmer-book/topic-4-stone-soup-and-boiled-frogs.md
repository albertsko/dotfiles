## Topic 4: Stone Soup and Boiled Frogs

Pragmatic programmers act as catalysts for positive change while remaining vigilant against gradual project decay.

The stone soup story illustrates how developers can spark collaboration. Requesting permission for large-scale changes often causes delays, bureaucratic committees, and resource hoarding. Developing a small, workable prototype demonstrates immediate value. Team members find it easier to join an ongoing success, making them eager to contribute additional resources once they see initial progress.

The boiled frog fable highlights the danger of subtle, incremental degradation. Major software disasters rarely occur overnight. Instead, project overruns and architectural decay accumulate one day at a time through small, unexamined changes, specification drift, and endless patches.

### The Pragmatic Approach

- **Be a Catalyst for Change**: Initiate small, functional improvements instead of seeking approval for massive overhauls upfront. Present a tangible working sample to build momentum and inspire team collaboration.
- **Remember the Big Picture**: Constantly monitor the overall system environment alongside daily individual tasks. Track gradual shifts in project requirements, performance, and code quality before minor issues compound into failures.

### Common Mistakes

- **Requesting Approval for Grand Scope**: Gaining authorization for massive architectural redesigns all at once, which causes startup fatigue, administrative delays, and resource guarding.
- **Ignoring Incremental Degradation**: Focusing strictly on narrow, immediate tasks while missing gradual specification drift, cumulative code patches, and declining project health.
