## 23. Design by Contract

Design by Contract (DBC) specifies the rights and responsibilities at each software boundary so a routine does no more and no less than it claims. Preconditions define what callers must make true before invocation, postconditions define what the routine guarantees upon termination, and invariants define the state callers can rely on before and after an operation even when internal processing temporarily breaks it. Invariants apply to state in any programming paradigm, not only to objects and classes. When a caller satisfies the preconditions, the routine must terminate with its postconditions and invariants restored; any violation is a bug that should trigger an agreed remedy, such as an exception or program termination, rather than serve as ordinary user-input validation. DBC complements testing without requiring setup or mocking: it defines success and failure for every execution, checks internal state throughout the software lifecycle, and assigns each validation responsibility once. Native contract support provides the strongest enforcement, and guard clauses can make invalid calls impossible to dispatch. Assertions, comments, and tests can preserve much of the design value in unsupported languages, but assertions do not automatically propagate contracts through inheritance, may be disabled or ignored, require manual checks of class and base-class invariants and saved entry-state values, and usually cannot cover library contracts even though library boundaries are frequent fault sites. Semantic invariants capture unchanging requirements that guide the whole system, while autonomous agents may use dynamic contracts to reject or renegotiate requests without abandoning explicit obligations and guarantees.

### The Pragmatic Approach

- Define each routine's valid input domain, boundary conditions, guarantees, and deliberate non-guarantees before writing its implementation.
- State preconditions for callers, postconditions for successful completion, and invariants for externally observable state.
- Require callers to validate external input and satisfy preconditions before invocation; when native support checks preconditions before routine entry, do not duplicate input handling inside the routine.
- Restrict direct mutation of data that participates in an invariant.
- Accept only clearly valid inputs and promise only what the routine can reliably deliver.
- Enforce contracts with native language features when available; otherwise bracket routines with assertion-based preambles and postambles, use guards where they can prevent invalid dispatch, preserve entry-state values needed by postconditions, and record unenforceable contracts in comments or tests.
- Treat every contract violation as a bug and fail at the point of violation with precise diagnostic information.
- Use contracts alongside tests so happy-path cases do not leave behavior under bad data, bad actors, bad versions, or bad specifications unspecified, or leave internal invariants unchecked.
- Identify requirements that define the system's meaning, state them clearly and prominently as semantic invariants, and keep changeable policies separate.
- Make dynamic agent contracts explicit: allow agents to reject requests or propose changed obligations, and record the resulting guarantees.
