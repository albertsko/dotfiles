---
name: go-development-single-skill
description: Use when designing, implementing, debugging, optimizing, testing, or reviewing Go code, or upgrading Go versions and tooling.
---

Apply these rules in the context of the task and the supported Go versions. Preserve each rule's conditions, alternatives, and caveats.

1. Establish the task scope, supported Go versions, toolchains, and target platforms.
2. Screen all rules below. Apply relevant rules and resolve uncertain applicability by inspecting the affected code and its contracts.
3. Review the implementation against the applicable rules and run checks suited to the changes. Report findings with their G identifiers, supporting evidence, and any unresolved issues or checks that could not run.

- **G1** When designing for possible future requirements. Then Solve concrete current problems before adding abstractions. Reassess as demonstrated needs emerge, including credible future compatibility requirements. Because Speculative flexibility adds complexity without demonstrated value.

- **G2** When maintaining code over years. Then Optimize code for future readers through clear names, representations, and structure. Readability is contextual, not a single syntax rule. Readability is not formatting alone. Because Reading greatly outnumbers writing and maintenance spans time.

- **G3** When assigning an outer variable inside a nested block. Then Use assignment to the existing variable, or assign a distinctly named temporary back to it. Intentional shadowing, including err, can be acceptable. Inspect scope and use shadow analysis. Because Short declarations can silently create a different variable and leave the outer value unchanged.

- **G4** When branches handle errors or exceptional inputs. Then Return early, omit else after returning branches, and keep normal execution aligned left. Apply to simplify actual flow. Preserve observable behavior when restructuring control flow. Because Less nesting reduces the mental model required to follow the function.

- **G5** When using several init functions. Then Express initialization dependencies explicitly. Keep within-package initialization independent of source-file order, which renaming can change. Use blank imports deliberately for intended registration side effects. From Go 1.21, independent packages initialize in import-path order when their dependencies are ready. Because Renaming source files may change initialization order.

- **G6** When initialization can fail or depends on external systems. Then Use an explicit initialization function that accepts dependencies and returns values and errors. Nonfailing static configuration is a reasonable init use. Return initialized values as well as errors so state ownership remains explicit. Retry and fallback remain caller decisions. Because Callers retain retry and fallback choices, tests avoid automatic external setup, and state can be encapsulated.

- **G7** When storing initialized state. Then Encapsulate state instead of assigning mutable package globals. Static initialization need not create globals. Because Global mutation couples functions and prevents isolated tests.

- **G8** When exposing struct data. Then Use direct fields unless accessor methods add useful behavior or representation hiding. Validation, computed values, debugging, locking or other synchronization, and credible forward compatibility can justify accessors even before the field representation changes. Because Mechanical getters and setters add unnecessary code.

- **G9** When naming accessor methods. Then Name getters after the property and setters SetProperty. Example Balance and SetBalance. Because These names follow Go conventions.

- **G10** When several implementations share meaningful behavior. Then Extract a small behavioral interface to factor common logic. Choose a demonstrated abstraction such as io.Reader or sort.Interface. Examples such as io.Reader, io.Writer and sort.Interface illustrate useful behavior boundaries, not an exhaustive set of interface uses. Because Algorithms become reusable across compatible concrete types.

- **G11** When tests or other callers need replaceable dependencies. Then Depend on an interface covering the required behavior and inject its implementation. Integration tests remain useful alongside unit tests. An injected test double does not verify the actual external implementation. Retain integration tests when needed. Because Production implementations and test doubles can be substituted.

- **G12** When a component must only use part of another type's behavior. Then Accept a restricted interface, such as a configuration getter. The concrete object can still expose other behavior elsewhere. A narrow consumer interface restricts the local API, not mutation through other aliases. The same concrete object may expose more capabilities elsewhere. Because The component cannot accidentally invoke mutation through that interface.

- **G13** When considering a new interface. Then Create interfaces for present, demonstrable needs and remove interfaces with no clear benefit. A proven reusable abstraction can be designed upfront. Usually small interface dispatch overhead is not the main reason to reject a purposeless interface. One existing implementation does not invalidate an established abstraction. Because Unneeded indirection makes code harder to follow.

- **G14** When a consumer needs to abstract a producer. Then Define a minimal interface in the consumer package and keep it unexported when local. Producer-side abstractions are valid when their reuse is already proven. Keep those minimal too. An established producer-side contract, including encoding interfaces, can be appropriate when usefulness across consumers is already demonstrated. Because Each consumer chooses its own methods without forcing unused methods on others.

- **G15** When designing function signatures. Then Usually return concrete types and accept useful interfaces. error and established abstractions such as io.Reader are legitimate interface returns. Because Clients retain flexibility and dependency cycles are less likely.

- **G16** When inputs or outputs belong to known types. Then Use explicit types rather than any, even if this requires separate methods. Use any for truly arbitrary values, such as serialization, formatting, or query parameters. Because Signatures communicate behavior and preserve compile-time safeguards.

- **G17** When writing generic APIs. Then Constrain type parameters to needed operations. Use ~T to admit types with underlying type T, and comparable for map keys. Generic functions and types require Go 1.18 language support. Methods with their own type parameters require Go 1.27 language support. Interface methods still cannot declare type parameters, and generic methods do not implement interface methods. Go 1.20 permits interface-containing comparable arguments, but dynamic comparisons can still panic. Because Constraints retain compile-time safety while admitting intended types.

- **G18** When typed collections or common algorithms would duplicate code. Then Use generics to factor reusable data structures or behavior without sacrificing type safety. Wait for concrete duplication or a real need. Examples include typed data structures, channel/slice/map operations and shared behavior with comparison functions. Because Avoids repeated implementations and runtime type checks.

- **G19** When a function only calls a required interface method. Then Accept the interface directly instead of introducing a type parameter. Reconsider any generic design that makes code less clear. Because The type parameter adds abstraction without value.

- **G20** When considering an embedded struct field. Then Embed only to intentionally promote useful behavior. Use named fields for private implementation details. Embedding is composition, not subclassing. The embedded object remains the receiver. Removing forwarding boilerplate is useful only when promotion belongs to the intended API. Shorter selectors alone do not justify embedding. Intentional promotion can implement interfaces without repetitive forwarding methods. Because Embedding exports promoted methods and can leak locking or other internals.

- **G21** When an exported type embeds another evolving type. Then Review additions to the embedded type for unintended API exposure. A team can choose to avoid embedding in public structs to avoid this maintenance burden. Because New inner methods are promoted automatically.

- **G22** When designing optional API configuration. Then Keep required constructor arguments explicit, and choose an extensible option mechanism with clear defaults. Configuration structs, builders and functional options are valid alternatives. Distinguish omitted and explicit zero options. Because Growing positional argument lists break existing callers and obscure which options are required.

- **G23** When options should be convenient and extensible. Then Use variadic functional options that update private configuration, validate inputs, and return errors before construction. WithX is a convention, not a universal requirement. Preserve meaningful zero values. Apply and validate options before creating the resource. WithX naming is conventional, not mandatory. Because Callers can omit all options for defaults and add options without changing existing calls.

- **G24** When choosing repository structure. Then Choose and consistently apply a layout suited to the project and organization. project-layout is optional and unofficial. Small projects and established organization layouts need no migration. Because Consistency reduces navigation costs across repositories.

- **G25** When separating programs, private implementation, and assets. Then Use purposeful directories such as cmd for executables and internal for code other applications must not import. A broader pkg/test/assets layout is optional rather than a Go standard. Place contracts, documentation, examples, configuration, tests, scripts and build assets in purposeful directories when needed. Do not add a generic src directory by habit. Because Directory meaning aids navigation and internal controls import visibility.

- **G26** When splitting packages. Then Delay packaging until responsibilities are understood and balance cohesion against oversized or tiny fragmented packages. Small highly cohesive packages can be valid. Nested directories do not confer privileged access. Both context-based and layer-based package organization can work if used consistently. Because Premature and excessive splitting obscures logical connections.

- **G27** When naming packages. Then Use short meaningful lowercase names describing what a package provides. Keep context-based or layer-based organization consistent. Because Names tell clients the package's purpose.

- **G28** When deciding what to export. Then Default to unexported elements and expose only required API. Serialization may require exported fields. Because A small public surface reduces coupling.

- **G29** When a package is named utils, common, shared, or base. Then Move functions to cohesive packages with meaningful names, or combine logically connected packages. Avoid replacing one utility package with arbitrary nano packages. A small naturally independent and cohesive package remains valid. Because Generic names hide responsibilities.

- **G30** When a package name already supplies type context. Then Remove redundant name fragments and consider methods on a meaningful type. Use types when they clarify the API, not merely to reduce characters. Because Qualified names become concise and expressive.

- **G31** When representing a set. Then Use map[K]struct{} when values carry no information. K must be an allowed map key. Because The empty value communicates that only key membership matters.

- **G32** When a local name matches an imported package or builtin. Then Choose another meaningful variable name or alias the import. Avoid dot imports in most cases because they obscure provenance. Because Shadowing blocks the original name and confuses readers.

- **G33** When exporting an API element. Then Document it with a complete sentence beginning with its name and explain intent and usage. Implementation mechanics belong in internal comments. Because Consumers should not need implementation reading to use the API.

- **G34** When deprecating an API. Then Add a Deprecated: comment that identifies the preferred replacement. Retain useful ordinary documentation. Because Tools can surface deprecation to users.

- **G35** When documenting constants or variables. Then Put purpose in public documentation and implementation-specific content explanations beside the declaration. Avoid exposing irrelevant representation details. Because Clients and maintainers need different information.

- **G36** When documenting a package. Then Add an adjacent Package name comment with a concise first line and details after it. Use a relevant source file or doc.go. Detached comments are omitted. Because Generated documentation makes scope and constraints discoverable.

- **G37** When maintaining a Go project. Then Choose useful analyzers and automate them in CI or hooks. Linters cannot detect every mistake. Examples include vet/shadow, errcheck, gocyclo, goconst and golangci-lint. Select useful checks rather than mandating historical tools. Because Checks find avoidable bugs such as shadowing and unchecked errors.

- **G38** When maintaining formatting consistency. Then Run gofmt and an import formatter such as goimports automatically. An aggregator can coordinate linters and formatters. Because Consistent formatting reduces review noise.

- **G39** When writing octal literals such as permissions. Then Use the explicit lowercase 0o prefix. Other bases have explicit prefixes too. Recognize legacy leading-zero octal when reviewing existing code. Because A leading zero alone is easily mistaken for decimal and uppercase O resembles zero.

- **G40** When writing long numeric literals. Then Use underscore separators to improve readability. Choose meaningful grouping for the representation. Because Digit grouping makes magnitude or bit groups easier to inspect.

- **G41** When choosing integer types or converting large values. Then Choose a sufficient range and check runtime overflow where values may exceed it. int and uint widths depend on the platform. Small types, large numbers, and conversions deserve particular attention. Do not add elaborate guards to ordinary counters whose chosen type safely covers the known domain. Because Runtime overflow and underflow are silent, unlike invalid constants.

- **G42** When incrementing a bounded integer. Then Check against the matching maximum before incrementing when overflow must be detected. Panic versus returned-error policy depends on the API. Use matching math limits, including architecture-dependent MaxInt or MaxUint where relevant. Because The maximum plus one wraps rather than panics.

- **G43** When adding bounded integers. Then Check both upper and lower bounds before signed addition when the input domain can overflow. A check of a > MaxInt-b is only safe under suitable positive-operand assumptions. Choose panic or an error according to the API contract. Because Positive addition can wrap to a negative result.

- **G44** When multiplying bounded integers. Then Validate the result range, handling zero, one and minimum-integer edge cases before any division-based verification. A conservative minimum-value guard alone is not a complete reusable validator. Use math/big when the domain exceeds fixed-width integers. Choose error or panic policy for the API. Because A wrapped result can silently corrupt arithmetic.

- **G45** When comparing approximate floating-point results. Then Compare within an acceptable delta instead of assuming exact equality. Choose tolerance for the domain. InDelta is a test-helper example. Because Representation and accumulated errors can differ, including across processors.

- **G46** When a numeric domain can produce special floating values. Then Check math.IsInf and math.IsNaN explicitly. Special values are not ordinary finite numbers. Because NaN does not equal itself and undefined operations need deliberate handling.

- **G47** When accumulating floating-point additions and subtractions. Then Group similar magnitudes before combining different magnitudes. Evaluate actual numerical behavior for the domain. Similar-magnitude grouping remains an accuracy heuristic. Results still approximate real arithmetic. Because Operation order affects rounding error.

- **G48** When reordering mixed floating-point operations for accuracy. Then Consider algebraic regrouping, including multiplication/division before addition/subtraction, only after checking numerical error and cost for the actual expression. Algebraic regrouping supplies no universal accuracy guarantee. Because Algebraic regrouping can change rounding.

- **G49** When indexing or appending slices. Then Reason separately about length, capacity, and the shared backing array, and retain append's returned slice. Growth factors are runtime details, not a correctness contract. Only the slice returned by append gets the updated length. Copying or reassigning a header does not update other headers. Because Indexes are limited by length. Append may reuse storage or allocate and copy, changing alias relationships.

- **G50** When the output slice size is known. Then Preallocate length and assign by index, or preallocate capacity and append. Index assignment can be faster. Capacity plus append can be clearer for complex index mappings. Because Avoids repeated allocation and copying during growth.

- **G51** When filtering yields an uncertain output size. Then Choose preallocation based on expected retained proportion and CPU versus memory cost. Benchmark performance-sensitive choices. There is no strict rule. Because Full preallocation may waste memory, while repeated growth costs work.

- **G52** When building an initially empty result of unknown final length. Then Prefer the zero-value nil slice and append as needed. Use make for known size, and literals for initial elements. Allocation claims need implementation review. Nil slices also support len and range. A non-nil empty result may still be necessary to honor a boundary contract. Because Nil slices are usable without defensive non-nil initialization.

- **G53** When passing slices to serializers, reflect, or libraries. Then Preserve the boundary contract for nil and non-nil empty values. encoding/json v1 emits null versus [] and reflect.DeepEqual distinguishes them. Go 1.27 JSON v2 is a separate API with different defaults, so test its chosen options rather than transferring v1 assumptions. Because JSON emits null versus [] and DeepEqual distinguishes them.

- **G54** When checking whether slices or maps contain elements. Then Test len(collection), not collection != nil. Nil checks answer a different question. Because Both nil and non-nil empty collections have no elements.

- **G55** When designing collection-returning APIs. Then Avoid giving nil and empty collections different meanings unless the contract requires it. Serialization contracts can require the difference. Because Callers otherwise face subtle unnecessary distinctions.

- **G56** When copying a slice. Then Allocate enough destination length and call copy(destination, source). Appending source elements to a nil slice is an alternative. Prefer copy for readability. Element copying does not recursively clone referenced objects. Because copy transfers only min(len(dst), len(src)) elements, regardless of capacity.

- **G57** When passing a subslice to code that may append. Then Limit capacity with a full slice expression or pass a copy. Capacity limiting still shares in-range elements. Copy when full independence is needed. A full slice expression also does not release the original backing allocation. Because Appending within spare capacity can overwrite elements outside the subslice's length.

- **G58** When keeping a small portion of a large slice long term. Then Copy retained elements to a new small slice. A full slice expression restricts append but does not release the old allocation. Because A subslice keeps the full backing allocation reachable.

- **G59** When removing elements containing pointers from a retained backing array. Then Copy retained elements or clear unused pointer-bearing slots before reslicing. Choose by future capacity, number of elements touched, measured cost and alias ownership. clear requires Go 1.21. From Go 1.22, slices.Delete/DeleteFunc/Compact/CompactFunc/Replace zero their obsolete tail. Retain the returned slice and account for aliases observing that clearing. Because Unreachable-by-length elements still retain referenced objects through the live backing array.

- **G60** When the expected map population is known. Then Provide the expected size to make. The size is a hint. Internal bucket details can change. A size hint is neither an initial length nor a maximum map size. Because Avoids repeated map growth and redistribution.

- **G61** When a long-lived map remains large after a temporary spike. Then Consider rebuilding a smaller map and releasing the old one. Copying temporarily requires additional memory until collection. Fixed-size caches may not need this. The temporary peak can approach the storage for two maps until collection. Rebuild only when retention matters. Because Deleting entries does not necessarily release the map's backing storage.

- **G62** When map values make retained storage expensive. Then Measure whether pointer values reduce retained storage enough to justify extra allocations and indirection. Deleting an entry can release its separate referent while map storage remains. Bucket counts and the 128-byte indirection threshold are historical implementation details. Go 1.24 changed built-in maps to Swiss tables, so measure on the target runtime. Because Pointer-sized slots can be much smaller than large inline values.

- **G63** When comparing values with == or !=. Then Verify comparability recursively and inspect dynamic interface values. Slices and maps support nil comparison but not ordinary equality. Pointers and channels compare identity. Go 1.20 comparable constraint satisfaction can admit interfaces whose dynamic values still panic on comparison. Struct/array comparison proceeds in order and short-circuits. Because Slices and maps cannot be compared this way, and interfaces holding noncomparable types can panic.

- **G64** When comparing composite values. Then Choose comparison semantics deliberately and read DeepEqual's type-specific behavior. For tests, go-cmp or testify can help. Performance-sensitive paths may need a custom comparison. Choose explicit equality semantics for floating fields, including a domain-appropriate tolerance where needed. Because DeepEqual supports composites but distinguishes nil and empty and incurs reflection overhead.

- **G65** When implementing a performance-sensitive comparator. Then Check standard library comparisons before writing a custom field-by-field comparator. bytes.Compare is one example. Ensure floating fields use domain-appropriate semantics. Test-oriented comparison libraries and production comparators have different cost requirements. Because Existing optimized operations avoid reinvention, while explicit comparisons avoid reflection costs.

- **G66** When mutating slice elements in a loop. Then Iterate indexes and update the original element. Pointer elements or pointer-valued fields share referents. Pointer slices may cost cache locality. Because The range value is a copy and assigning its fields does not replace the stored struct.

- **G67** When iterating every collection element. Then Use range and omit unused values or use the blank identifier. Use a traditional for loop when controlling step or termination is useful. Because Avoids unnecessary index management and off-by-one mistakes.

- **G68** When a range loop changes its input expression. Then Reason from the initially evaluated range expression, including original slice length or channel. Reassignment or append does not retarget the active range. If at most one iteration variable is present and x or len(x) is constant, the range expression x is not evaluated. Use a traditional loop for a changing condition, checking termination when appending. Later operations on a reassigned channel use its new value. Because The loop works from the evaluated expression, such as the original slice length or channel.

- **G69** When ranging over an array while observing mutations. Then Use direct index access or range over the array pointer when later updates must be seen. A pointer also avoids copying a large array. Because Ranging values over an array copies the array.

- **G70** When retaining addresses of slice or map iteration values. Then Check the effective module/file language version. Go 1.22+ gives fresh per-iteration variables when the loop declares them with :=, including three-clause loops. Assignment with = still reuses existing variables. In older language modes or with explicitly shared variables, copy the value or pass it as an argument. Distinct value copies differ from pointers to original slice elements obtained by index. Slice range visits increasing indexes. Map iteration order is unspecified. Fresh variables do not determine goroutine scheduling order. Because Loop declaration semantics control variable identity, while pointers into a slice intentionally share its elements.

- **G71** When depending on order from a map. Then Do not assume key, insertion, stable, or uniformly random iteration order. Choose an ordered representation when required. A serializer may impose its own ordering, which is not a map property. Unspecified ordering supplies no fairness or uniform-randomness guarantee. Because Map iteration is unspecified and can vary across loops.

- **G72** When adding map entries while iterating. Then Separate the map being read from the map being written when deterministic inclusion matters. A copy can serve as the destination. Single-goroutine mutation permission is not concurrency safety. Adding entries within the same goroutine is legal but does not control whether the new entries are visited. Because New entries may be visited or skipped unpredictably.

- **G73** When breaking or continuing an outer loop containing switch or select. Then Use a meaningful label to target the intended loop. Labels for structured loop control are idiomatic. Because An unlabeled break exits the innermost for, switch, or select.

- **G74** When each loop iteration acquires a resource needing cleanup. Then Extract iteration work into a function and defer cleanup there. A closure also works. If measured call overhead matters, clean up explicitly on every path. An extracted helper also makes iteration work independently testable. Because Defers run on function return, not on each iteration.

- **G75** When processing text or binary data represented as a string. Then Distinguish bytes, Unicode code points, and encoding. Do not assume arbitrary input is UTF-8. External encodings may need dedicated decoding. A Unicode code point is not necessarily a whole user-perceived character. Source-literal UTF-8 statements have escape-related limits. Because Strings hold arbitrary bytes and len counts bytes, while runes are code points.

- **G76** When iterating UTF-8 runes. Then Use the range value as the rune and treat the index as a byte offset. Range avoids an unnecessary []rune allocation. Known single-byte text may be accessed directly as bytes without rune conversion. Because s[i] accesses a byte, not a complete multibyte rune.

- **G77** When counting or indexing Unicode code points. Then Use utf8.RuneCountInString for rune counts and a rune slice for rune-indexed access. Rune slices allocate and decode. Direct byte access is valid for known single-byte text. For traversal rather than random rune indexing, direct range avoids a rune-slice allocation. Because Byte length and byte indexes do not describe variable-width code points.

- **G78** When removing exact leading or trailing text. Then Use TrimPrefix or TrimSuffix for one exact affix, and TrimLeft/Right/Trim for a set of runes. TrimSuffix and TrimPrefix remove at most one matching affix. Because Cutset trimming repeatedly removes any member, not an exact substring.

- **G79** When concatenating many strings, especially in a loop. Then Use strings.Builder for repeated concatenation, and Grow when the total byte count is known. For a few fixed strings, + or formatting may be clearer. Measure performance-sensitive cases rather than treating a five-string heuristic as a threshold. Because Repeated concatenation allocates and copies immutable strings.

- **G80** When writing through a strings.Builder. Then Confine a strings.Builder to one goroutine or synchronize access. Use WriteString, Write, WriteByte or WriteRune for the actual input. WriteString's error is always nil, so deliberate omission is justified. Do not copy a non-zero Builder. Because Its internal append operations are not safe for concurrent mutation.

- **G81** When a workflow starts and ends with byte slices. Then Use bytes package operations throughout instead of converting to strings and back. Check available operations before assuming strings are more convenient. Compiler optimizations may alter allocation details. Evaluate the whole workflow, including byte-oriented I/O at either boundary. Preserve string immutability when reasoning about conversion optimizations. Choose the byte/string representation for the complete workflow. This is not a universal ban on strings. Because Conversions can add allocation and copying.

- **G82** When slicing a string by textual position. Then Use rune-aware handling for rune boundaries instead of arbitrary byte slicing. Byte slicing is appropriate for fixed ASCII fields such as UUIDs. Validate the length of a fixed-byte format before indexing it, as with a UUID field. Because String slice indexes count bytes and may split multibyte encodings.

- **G83** When retaining a small substring of a large string. Then Use strings.Clone (Go 1.18+) when independent backing storage is needed. Passing by value copies the string header, not its bytes. Storage sharing is implementation-dependent. Preserve intentional copies and verify older string([]byte(fragment)) copy idioms against compiler optimization. Because Substring storage can retain the entire source allocation.

- **G84** When a method changes receiver state or contains noncopyable synchronization state. Then Use a pointer receiver. Appending to a slice receiver requires updating its header. Indirect fields can mutate even through a value receiver. Because Value receivers copy the receiver and can lose mutations or duplicate synchronization objects.

- **G85** When choosing receivers for naturally small value types. Then Prefer value receivers for small natural value types, immutable structs/arrays, and slices whose header need not change. Copying a slice, map or pointer still shares referents. Choose receiver semantics deliberately. Named map, function and channel types can have pointer receivers. Because Value receivers express direct value semantics without unnecessary pointers.

- **G86** When choosing receiver kinds and consistency across a type. Then Keep receiver kinds consistent unless interface requirements or actual semantics justify mixing, as with time.Time unmarshaling. Consider mutation, noncopyable state, size and indirect sharing. Pointer receivers can signal indirect mutation. Resolve uncertainty from these conditions rather than conflicting value-default and pointer-when-unsure heuristics. Because Consistency makes mutation expectations clearer.

- **G87** When several return values have unclear meanings, especially identical types. Then Name result parameters to document their meanings, or return a struct with meaningful fields. Naming an obvious error alone may add no value. Existing interfaces may preclude changing results to a struct. Because A signature can distinguish latitude from longitude without reading implementation.

- **G88** When using named results in an implementation. Then Use them sparingly for clear readability or convenience benefits and keep naked returns confined to short functions. Be consistent about explicit versus naked returns within a function. Named results do not require naked returns. Named result zero initialization can occasionally simplify a short implementation. Naming an obvious error alone need not improve the signature. Because Long functions force readers to track hidden result state.

- **G89** When returning a named result after a failing call or condition. Then Assign or return the actual error instead of an untouched named error variable. An explicit local assignment can prevent the mistake. Because Named results start at zero and can silently return nil despite failure.

- **G90** When returning an interface, particularly error, from a pointer value. Then Return literal nil explicitly when the underlying pointer is nil. Applies to all pointer-implemented interfaces. Nil receiver methods are allowed but must avoid unsafe dereferences. Because A typed nil pointer inside an interface makes the interface non-nil.

- **G91** When a function processes stream content. Then Accept io.Reader instead of a filename or concrete file type. Filesystem-opening functions such as os.Open appropriately accept filenames. Move resource opening and closure ownership to the caller or resource boundary. Because The algorithm works with files, network bodies, and in-memory test inputs.

- **G92** When deferred work must see a variable's final value. Then Use a closure reading the variable at execution, or deliberately pass a pointer. Passing a closure argument still evaluates that argument immediately. Pointer-based changes may require API changes. Because Ordinary defer arguments are evaluated immediately.

- **G93** When deferring a method call before modifying its receiver. Then Account for immediate receiver evaluation and value versus pointer copying. Reassigning a pointer variable does not retarget the already captured pointer. Because A value receiver sees the captured copy, while a captured pointer sees later changes to its referent.

- **G94** When reporting normal operational failure. Then Return an error as the final result rather than emulating exceptions with panic and recover. Reserve panic for exceptional programmer errors or unusable mandatory dependencies. The error belongs last in an ordinary result list. A mandatory dependency may justify panic when failure leaves the operation unusable, as in a fixed regular expression. Because Callers can handle expected failures explicitly.

- **G95** When a deliberate panic recovery boundary is needed. Then Call recover directly in a deferred function executing in the panicking goroutine. A helper called by that function does not provide direct recovery, and another goroutine cannot recover the panic. Use errors for normal failures. Go 1.21 defaults turn panic(nil) into *runtime.PanicNilError, but panicnil=1 or program compatibility defaults for Go <=1.20 preserve the old nil result. Inspect the active workspace or work-module defaults and explicit overrides. Per-file language gates do not select these runtime defaults. Because Ordinary recover calls do not intercept a panic.

- **G96** When returning an error from a lower layer. Then Return it directly when no context or classification is useful, or add useful context with %w. Avoid noisy redundant context. Because Context improves diagnosis while preserving the underlying error.

- **G97** When callers need an error category or extra structured information. Then Use a custom error type with the required context and deliberate source access. Expose or unwrap the cause only when it is part of the contract. Because A type supports classification beyond a message.

- **G98** When the underlying error is an implementation detail. Then Transform the error, for example with %v, rather than exposing it through wrapping. Use %w when cause inspection is intentionally supported. A transformed message can still add diagnostic context. Error classification and exposure of an underlying cause are separate API decisions. Because Wrapping lets callers depend on the cause and couples them to implementation choices.

- **G99** When matching an error type that may be wrapped. Then Use errors.As with a non-nil pointer target whose element is an error-implementing type or an interface. A *error variable passed directly as the target is a common misuse diagnosed by vet. Go 1.26+ offers errors.AsType[T] for typed extraction. Is/As traverse multi-error trees from Go 1.20. A type switch only examines the outer error. Because A type switch only sees the outer error and can misclassify wrapped failures.

- **G100** When matching a sentinel error that may be wrapped. Then Use errors.Is instead of direct equality. Direct comparison can be valid where an API explicitly returns the sentinel unwrapped. Matching error text is not a substitute for error identity. Because The sentinel may live inside a wrapper.

- **G101** When designing recognizable errors. Then Use named sentinel values for expected conditions and custom types for richer unexpected failures. Treat this as a general guideline, not an exhaustive taxonomy. Use recognizable Err-prefixed names. Structured expected errors can also be legitimate. A non-error sentinel result, such as an absent collection, may fit a domain contract. Because Callers can check stable expected conditions and inspect structured error information.

- **G102** When propagating a failure through layers. Then Handle it once: return it with useful context or log it at the handling boundary. Preserve source/target distinctions through contextual wrapping. The single-handling rule addresses the same propagated failure, not a separate failure during cleanup. Because Repeated logging duplicates events and can interleave confusingly under concurrency.

- **G103** When an error is intentionally safe to ignore. Then Assign it to the blank identifier and explain a non-obvious reason. Ignoring should be exceptional. Comments should explain why, not repeat syntax. Because Readers can distinguish intentional omission from forgotten handling.

- **G104** When a deferred cleanup can fail. Then Choose explicitly to handle, propagate, or deliberately ignore its error, often using a deferred closure. Logging may be appropriate for a cleanup-only failure. Returning from a deferred closure does not return from the surrounding function. Because A plain deferred call silently drops the returned error.

- **G105** When propagating cleanup failure through named results. Then Preserve the primary error and report meaningful cleanup failure separately or combine them. On Go 1.20+, errors.Join retains multiple causes for Is/As traversal. Otherwise use a deliberate custom aggregate or retain the primary error and log cleanup failure. Never overwrite a primary error with a nil cleanup result, and log closeErr rather than the unrelated primary variable. Because Unconditional assignment can replace a real failure with nil.

- **G106** When designing concurrent work. Then Separate work structure and coordination from simultaneous execution, and parallelize actual bottlenecks. Adding workers to a non-bottleneck stage may not improve throughput. Because Concurrency enables independent stages, while parallelism adds execution capacity.

- **G107** When considering parallel execution. Then Begin with a simple sequential version unless measurements justify concurrency. Goroutines are lightweight, not free. Profile and benchmark in a production-like environment. Scheduling, queuing, stack memory, context switches and contention all contribute overhead. Historical scheduler timings, initial stack sizes and G/M/P descriptions are explanatory, not tuning contracts. Because Goroutine creation, scheduling, contention, and coordination can outweigh work.

- **G108** When recursively splitting or scheduling very small jobs. Then Use a measured granularity threshold and keep small jobs sequential. The threshold is machine- and workload-dependent. A fixed threshold of 2048 is not universal. Because Tiny tasks can cost less than their scheduling overhead.

- **G109** When choosing a concurrency primitive. Then Use mutexes for exclusive access to shared state and channels for communication, coordination, or ownership transfer. They are complementary. A parallel/concurrent classification is a heuristic, not a channel synchronization prohibition. Because The primitives express different responsibilities.

- **G110** When multiple goroutines access shared memory and one writes. Then Use suitable atomic operations, one mutex protecting the critical section, or a single owner receiving messages. Atomicity of an individual operation does not make a whole algorithm correct. Protect reads as well as writes and synchronize before observing completion. Multiple individually atomic operations do not automatically protect a compound invariant. Because Unsynchronized read/write combinations cause data races and invalid results.

- **G111** When output depends on execution ordering. Then Coordinate the required sequence explicitly, even after removing data races. Use channels or another sequencing design when state transitions must happen in order. Mutual exclusion alone does not choose which independently scheduled assignment should win. Because A race-free program can still have timing-dependent logical results.

- **G112** When publishing data between goroutines. Then Establish an actual happens-before path through synchronization. Reason about channel send/receive and observed closure precisely. A send happens before completion of its matching receive. Closing a channel happens before a receive that observes closure. Because Launching establishes startup ordering, but goroutine exit alone does not publish completion.

- **G113** When changing an unbuffered channel to a buffered one. Then Recheck ordering assumptions in both directions. A send still precedes completion of its corresponding receive. Closing precedes a receive observing closure. Because Unbuffered receive-before-send-completion guarantees do not simply carry over to arbitrary buffering.

- **G114** When processing many tasks concurrently. Then Use a bounded worker pool rather than unbounded per-task goroutines. Close the job channel and wait for workers when work finishes. Because Limits resource use and pressure on downstream systems.

- **G115** When choosing worker count. Then Start CPU worker counts near runtime.GOMAXPROCS(0), then measure. Size I/O work around downstream sustainable capacity. NumCPU may differ. Go 1.25+ runtime defaults can track CPU availability and Linux quotas, but older module defaults and explicit overrides affect that behavior. Mixed workloads need measurements. Because CPU work is limited by available execution capacity, while I/O work waits on external systems.

- **G116** When an operation becomes useless after a time limit. Then Derive a deadline or timeout context from the existing parent and pass it to context-aware operations. Use Background only for a deliberate root when no parent exists. Cancellation is cooperative. Because Allows stale or stalled work to stop.

- **G117** When creating a cancelable or timed context. Then Call the returned cancel function on every exit path when the owning work is done, commonly with defer. Do not assume that creating a cancellable context always creates a goroutine. Because Releases associated resources earlier than eventual timeout.

- **G118** When a long-running activity must stop with its owner. Then Propagate a cancellation context and arrange graceful resource cleanup. Signaling cancellation alone does not prove cleanup completed. Because Cancellation communicates lifecycle termination.

- **G119** When context values need stable keys across packages. Then Use an unexported custom key type and controlled key values. Values are suited to cross-boundary information such as tracing or middleware metadata. WithValue derives a child context instead of mutating its parent. Keep key values controlled as well as using a private key type. Because Plain string keys can collide between packages.

- **G120** When implementing context-aware channel operations. Then Select between the send or receive and ctx.Done, then report ctx.Err on cancellation. Done is a broadcast closure signal. Err distinguishes deadline from cancellation. Check channel closure and other protocol conditions separately from cancellation. Standard contexts can be shared concurrently. Because A blocking channel operation otherwise prevents prompt cancellation.

- **G121** When designing a function callers may wait for. Then Accept a context so upstream callers can control cancellation. Use TODO when the right context is not yet clear, rather than disguising the uncertainty as Background. TODO identifies incomplete propagation. Background states an intentional root. Because Long-running work needs caller-controlled lifetime.

- **G122** When launching work that must outlive an HTTP request. Then Give detached work an explicit owner, lifetime bound and completion path. From Go 1.21, context.WithoutCancel preserves values while removing cancellation and deadline, and its Done channel is nil. Add a fresh cancelable/timeout context when needed. On older versions, choose a deliberate root or a carefully defined value-preserving wrapper. Request completion must not accidentally terminate required background work. Because Request cancellation or handler completion can abort asynchronous publication.

- **G123** When starting any goroutine. Then Identify its exit condition and the owner responsible for stopping it. A receive loop requires a known channel closure or cancellation path. Because Leaked goroutines retain stacks, referenced memory, and external resources.

- **G124** When shutting down a service or goroutine owning resources. Then Wait for cleanup to finish before the parent or application exits. Provide a close/join lifecycle appropriate to the component. A synchronous Close can provide the join guarantee when it actually releases owned resources before returning. Because A cancellation signal alone does not guarantee cleanup completes.

- **G125** When goroutines capture loop variables. Then Check the effective module/file language version. Go 1.22+ gives fresh per-iteration variables when the loop declares them with :=, including three-clause loops. Assignment with = still reuses existing variables. In older language modes or with explicitly shared variables, copy the value or pass it as an argument. Distinct value copies differ from pointers to original slice elements obtained by index. Fresh loop variables do not determine goroutine or parallel-subtest execution order. Because Capturing a shared variable can observe a later value and race. A new toolchain alone does not change an older file language mode.

- **G126** When selecting among multiple ready channels. Then Do not use case source order to express priority. A default branch only runs when none can proceed. A ready case is chosen pseudo-randomly. This does not make case order a priority mechanism. Default runs only when no other case can proceed. Because select chooses among ready operations rather than taking the first textual case.

- **G127** When one producer must deliver data before a termination event. Then Use one ordered event channel or a suitable unbuffered handoff. This ordering argument assumes a single producer. More than one producer needs additional coordination. A single-producer ordering argument is not enough. Because A separate buffered data channel can retain messages when termination is selected.

- **G128** When a termination signal should allow draining already available messages. Then After termination, drain messages with an inner select and default before returning. Messages arriving after the drain can be missed. Handle closed channels and producer coordination deliberately. A closed channel remains ready and must be handled with the receive ok result to avoid endless zero-value draining. Because The drain consumes currently ready data without blocking indefinitely.

- **G129** When a channel conveys notification with no payload. Then Use chan struct{}. Choose actual data types when values do have meaning. Because The type communicates absence of data meaning and empty elements require no payload storage.

- **G130** When a select loop consumes channels that can close. Then Use the two-result receive and set closed input channels to nil to disable their cases. Exit when all inputs are disabled. Sending or receiving on a nil channel outside select blocks forever. Plan output consumption and cancellation too. Finish and close an owned output after all input channels are disabled. Because Closed channels remain ready and can cause zero-value streams or busy loops.

- **G131** When choosing buffered versus unbuffered channels. Then Use unbuffered channels when the protocol needs a rendezvous and buffering when justified by decoupling or bounded capacity. Buffered channels also have memory-model guarantees. An unbuffered channel is also sufficient for closure-only notifications because there is no payload queue to buffer. Because Buffering changes blocking and ordering behavior and may obscure deadlocks.

- **G132** When sizing a buffered channel. Then Start with a small justified capacity and tie larger capacities to worker count, a resource limit, or measurements. A default capacity of 1 is only a heuristic. Explain non-obvious sizes. Burst requirements can justify more capacity. Tie a buffer used for workers or rate limiting to the corresponding bound. Because Queue capacity trades memory against contention and rarely stays perfectly balanced.

- **G133** When formatting a context or object in concurrent code. Then Inspect what formatting traverses or calls, and prefer a stable explicit key over formatting mutable state. Mutable context values need their own synchronization. Because Formatting can read shared values and introduce data races.

- **G134** When formatting an object while holding its lock. Then Avoid invoking a String method that reacquires the same lock. Format safe fields directly or narrow lock scope. Test error branches that trigger formatting. Formatting can call methods implicitly. Test error branches that perform the formatting, even when validation looks trivial. Because The indirect method call can deadlock.

- **G135** When validation does not require shared mutable state. Then Validate before acquiring a mutex and keep critical sections focused. Validation that depends on protected state must remain synchronized. Because Avoids unnecessary locking and reduces indirect side effects.

- **G136** When concurrent goroutines append from a shared slice. Then Isolate backing storage or synchronize instead of relying on current spare capacity. A full slice can allocate separate arrays, but this fragile condition should not dictate correctness. Shared headers and elements need separate analysis. Synchronize shared slice-header writes as well as backing-array writes. Because Append can mutate shared backing storage when capacity remains.

- **G137** When partitioning concurrent collection access. Then Disjoint slice indexes may be handled independently, but synchronize concurrent map access involving writes. Pointer-referenced data or shared slice headers can reintroduce races. Different map keys do not provide isolation. Because Different slice cells are separate memory locations while map writes affect shared state.

- **G138** When reading shared slices or maps under a mutex. Then Protect the entire use or copy actual elements while locked, then work on the snapshot. Snapshots cost memory and copying. For pointer elements, copy depth must match mutation needs. For light work, holding the lock may be simpler than making a snapshot. For expensive processing, copying can reduce lock contention. Because Assigning the slice or map only copies a descriptor and leaves shared storage.

- **G139** When using WaitGroup with newly started goroutines. Then Register Add before launch and call Done on every worker exit, with consistent counts. On Go 1.25+, WaitGroup.Go combines registration and launch when its callback obeys the no-panic contract. When the group is empty, start work before Wait. Reuse only after the previous Wait returns. Wait joins work but does not itself cancel it. Because Wait may otherwise see zero and return before workers register.

- **G140** When many goroutines repeatedly wait for changing shared conditions. Then Consider sync.Cond instead of busy polling or assuming channel sends broadcast. Notifications are not queued for future waiters. Signal wakes one waiter. Channel closure broadcasts only once. One channel send reaches one receiver. Round-robin receiver distribution is not an ordering guarantee. Because Broadcast wakes all current waiters without a busy loop.

- **G141** When waiting on a sync.Cond. Then Hold its lock, test the predicate in a loop, call Wait, and recheck after waking. Update the condition under the same lock and signal/broadcast as appropriate. Because Wait unlocks while waiting and relocks before returning, while state can change before the waiter runs.

- **G142** When running several tasks with error propagation and cancellation. Then Use errgroup.WithContext, return errors from Go callbacks, and check Wait. Tasks must observe the derived context. Wait waits for all tasks, not merely the first failure. The group returns the first non-nil error rather than an aggregate. Cancellation is cooperative and Wait still joins every task. Because It coordinates completion and returns a failure while canceling shared work.

- **G143** When concurrent tasks produce ordered independent results. Then Preallocate a results slice and assign each task its own index. Read results only after task completion and avoid shared element referents. Index/value capture still must follow the applicable loop semantics. Because Preserves input ordering without a separate reorder stage and avoids overlapping writes.

- **G144** When passing, returning, or calling methods on synchronization-containing values. Then Share the same synchronization instance and avoid copying active Mutex, RWMutex, Cond, Map, Once, Pool or WaitGroup values. Inspect assignments, arguments, returns and receivers, including structs that contain them. Use initialized pointers where appropriate. Go 1.22 three-clause loops can implicitly copy newly declared variables each iteration, so keep no-copy state outside the loop. Because Copies create unrelated locks or corrupt coordination expectations.

- **G145** When reviewing code that uses sync types. Then Run go vet and inspect value receivers and arguments for accidental copies. Covers Mutex, RWMutex, Cond, Map, Once, Pool, and WaitGroup as discussed. Because Copies can be hidden inside enclosing structs.

- **G146** When supplying a duration. Then Use explicit time units such as time.Second or 100*time.Millisecond. time.Duration is a defined integer type, not an alias. Because Bare integers are nanoseconds and easily mistaken for milliseconds.

- **G147** When a hot loop or frequently called handler needs timeout logic. Then Determine program compatibility settings from the active workspace or work module and explicit overrides, as well as the runtime version. Before Go 1.23, and on Go 1.23-1.26 with older program defaults or asynctimerchan=1, coordinate Stop, any required drain and Reset with the sole receiver to prevent stale values and races. With Go 1.23 synchronous timer semantics (program defaults for Go >=1.23 unless overridden), Stop/Reset prevent later stale receives and unreachable timers/tickers can be collected. Go 1.27 removes asynctimerchan and uses synchronous channels even for old modules. Use nonblocking receive, not len/cap, to inspect readiness. Reuse only when measurement justifies the complexity. Because Repeated timers can add allocation work, but retention and channel-reset correctness depend on the active timer semantics.

- **G148** When a long-running timer consumer can terminate. Then Provide cancellation or another exit protocol and stop timers when their work should cease. Cancel recreated timeout contexts on every path. Under Go 1.23 synchronous timer semantics and all Go 1.27 runtimes, Stop is no longer needed solely to make an unreachable timer collectible. It remains useful for lifecycle control. Because An endless loop does not provide a production termination or cleanup protocol.

- **G149** When a serialized struct embeds a type with custom JSON methods. Then Use a named field or explicitly implement the parent marshaling behavior. Custom marshaling must stay synchronized with added fields. Because Promoted MarshalJSON/UnmarshalJSON methods can silently replace the parent object's representation.

- **G150** When comparing times after JSON round trips. Then Use time.Time.Equal for instant comparison. Equal uses monotonic readings if both operands have them, otherwise wall time. JSON removes monotonic metadata. If raw struct equality is deliberately required, normalize both monotonic metadata and location. Truncate(0) alone does not normalize location. Because Serialization drops monotonic metadata and representations may differ.

- **G151** When output must use a consistent time zone. Then Convert times to the chosen location or UTC before serialization. Handle LoadLocation errors. Because Local environment otherwise affects representation.

- **G152** When measuring elapsed time. Then Use monotonic clock behavior rather than wall-clock-only arithmetic. time.Time can carry both components. Use monotonic-aware time operations. Serialization discards that metadata, so serialized timestamps cannot preserve the same elapsed-time evidence. Because Wall clocks can jump forward or backward after synchronization.

- **G153** When decoding JSON into map[string]any. Then For encoding/json v1 decoding into map[string]any, expect float64 numbers by default and check dynamic types before assertions. Prefer typed decoding for known schemas. Select a decoder number mode when exact numeric handling requires it. Go 1.27 v2 has its own options and behavior, which require boundary tests. Because An integer-looking JSON number is not automatically a Go int.

- **G154** When startup readiness requires a reachable database. Then After sql.Open, call Ping or PingContext and handle failure. Behavior varies by driver. A context bounds the readiness check. Because Open can validate configuration without establishing any connection.

- **G155** When operating a database client in production. Then Reuse sql.DB as the connection pool and configure maximum open connections to match database capacity. Multiple pools may be appropriate for distinct workloads. Do not build a redundant manual pool around sql.DB or close the pool after every query. Because sql.DB is not a single connection and unlimited growth can overload the database.

- **G156** When tuning database connection reuse. Then Set idle count, idle time, and maximum lifetime for request concurrency, bursts, and load balancing. Select values for the actual workload. Tune idle count for concurrency, idle age to release post-burst capacity, and lifetime for rotation or balanced use of connections. Because Too few idle connections cause reconnects, while stale idle or long-lived connections consume resources or concentrate load.

- **G157** When repeating SQL or handling untrusted values. Then Use parameterized prepared statements where appropriate and keep values separate from SQL text. Parameterization and explicit preparation are separate concerns. Statements must be closed. Stmt is reusable and safe for concurrent calls in database/sql. Use context variants when cancellation matters and account for driver behavior. Explicit Prepare is not required merely to separate bound parameters from SQL text. Because Avoids repeated compilation and reduces injection risk.

- **G158** When scanning nullable database columns. Then Use pointer destinations or sql.NullXXX and check nil or Valid before using the value. Go 1.22+ also provides sql.Null[T]. Handle Scan errors separately from a valid SQL NULL. Because Scanning NULL into a plain scalar can fail.

- **G159** When finishing a rows.Next loop. Then Check rows.Err after iteration. Also handle query and Scan errors and close Rows. Handle query, Scan and meaningful Close errors as well as the iteration error. Because Next returning false means either exhaustion or failure.

- **G160** When an HTTP client call succeeds. Then Close the response body even when its contents are ignored. Check the request error first. A non-nil response returned with an error need not be closed under the documented client contract. The non-nil response with a client redirect error has an already closed body under the described contract. Server-owned request bodies have a separate ownership rule. Server request bodies are closed by the server rather than owned like client response bodies. Because An unclosed body retains resources and can prevent connection reuse.

- **G161** When only status matters and connection reuse is desired. Then Choose a bounded time/resource policy before draining an ignored body to io.Discard, and always close a successful client response body. Reading to EOF can permit reuse without storing the body. Go 1.27 HTTP/1 Close attempts only bounded draining, so unread arbitrary bodies do not guarantee reuse. Server request bodies remain server-owned. Because Reading to completion permits reuse without allocating the whole body.

- **G162** When a database query returns Rows. Then Arrange Rows.Close after successful acquisition, commonly with defer. sql.DB itself is intended to be long-lived and shared, with closure owned by its lifecycle. Because Returns the connection to the pool on early exits.

- **G163** When opening files. Then Close them explicitly and handle meaningful close errors. Propagate a close error if the primary write succeeded. Preserve prior failures. For a writable file, report Close failure when the primary write succeeded and preserve a preexisting write failure. Because Relying on garbage collection delays release and hides errors from pending writes.

- **G164** When file durability is required before return. Then Call Sync and handle its error. Sync costs performance. Review the contract before deciding whether to ignore Close errors after Sync. Because A successful Write or Close does not ensure data reached durable storage.

- **G165** When an HTTP error response should terminate a handler. Then Return immediately after http.Error. Test failing paths. Assert status and body on failure paths so repeated status writes, mixed success/error bodies and nil dereferences are detected. Because Writing a response does not stop execution and later code can append success data or dereference invalid values.

- **G166** When configuring a production HTTP client. Then Set request and relevant dial, TLS handshake, and response-header timeouts. Choose values for the workload, especially long-running responses. Client.Timeout includes reading the response body. One- or five-second timeouts are not universal values. Because Unbounded waits can exhaust resources.

- **G167** When an HTTP client makes many concurrent calls. Then Tune idle timeout, global idle count, and per-host idle count, and reuse connections. Distinguish idle limits from total active connection limits. Avoid losing useful transport defaults when customizing. Keep-alives should not be disabled casually. Preserve useful transport defaults and distinguish idle-pool limits from active-connection limits. Because Default per-host idle limits can force repeated reconnects.

- **G168** When serving untrusted or production HTTP traffic. Then Set ReadHeaderTimeout and appropriate request/body limits, then choose a handler-duration policy for the protocol. TimeoutHandler sends 503 and cancels its context, but does not stop arbitrary work and is unsuitable for streaming that needs its unsupported interfaces. Evaluate WriteTimeout and per-request ResponseController deadlines (Go 1.20+) for the actual response protocol. Do not dismiss WriteTimeout without evaluating the protocol. Because Slow or never-ending requests otherwise retain server resources.

- **G169** When keeping HTTP server connections alive. Then Configure IdleTimeout deliberately. Choose a value that balances reuse and resource limits. Because Otherwise ReadTimeout is used, or connections may have no idle bound.

- **G170** When organizing a testing strategy. Then Categorize tests so fast isolated tests and more expensive integration or end-to-end tests can be selected intentionally. The testing pyramid favors many fast deterministic unit tests but is a model, not a numeric quota. Because Unclassified suites waste time and hide the scope of verification.

- **G171** When a whole test file belongs to an optional category. Then Use a build constraint with the corresponding go test -tags invocation. Tagged runs also include untagged files. Negated tags can separate mutually exclusive categories. Excluded tests are not reported as skips. The available build-tag syntax depends on the supported Go version. Because Allows category-specific compilation and execution.

- **G172** When individual optional tests should report why they did not run. Then Check an explicit environment variable and call t.Skip with a reason. This differs from compile-time file exclusion and can coexist with tags. Arrange CI jobs so optional test categories actually run instead of remaining silently excluded indefinitely. Because Visible skips reduce the chance of forgotten tests.

- **G173** When some tests are slow even within a category. Then Use testing.Short and t.Skip, selected with go test -short. Per-test classification can combine with tags or environment gating. Short mode classifies speed, not unit-versus-integration scope. Because Provides a quick feedback mode without redefining test categories.

- **G174** When testing concurrent code. Then Run go test -race ./... in local testing or CI and investigate reports. It adds substantial overhead and does not prove absence of races. Broad production use is usually inappropriate. Inspect conflicting access and goroutine-creation stacks. Treat detector warnings as real race evidence. Clean runs can miss races. Because The runtime detector catches unsynchronized accesses on exercised paths.

- **G175** When a concurrency test only occasionally exercises the relevant schedule. Then Exercise concurrent paths thoroughly and consider repeated runs or iterations. Repetition improves chances but is not a correctness proof. !race can exclude incompatible tests, but exclusions reduce coverage and need justification. A !race tag removes validation coverage, not the underlying race. Because Dynamic detection can miss unexecuted or unsurfaced races.

- **G176** When independent tests spend meaningful time running. Then Mark appropriate tests with t.Parallel and tune -parallel for the workload. Parallel tests are paused until sequential work completes in the relevant scope. Shared state may prevent safe parallelism. Parallel tests pause until their parent scope releases them. Default test concurrency follows GOMAXPROCS. Because Can reduce total suite duration, especially for I/O-heavy tests.

- **G177** When checking test isolation. Then Run with -shuffle=on and preserve the reported seed when reproducing a failure. Use the numeric seed for the same ordering. Keep informed about available test modes. A shuffle seed reproduces ordering, not arbitrary goroutine scheduling or external-service state. Because Randomized order exposes hidden dependencies on execution order or shared variables.

- **G178** When many cases use the same assertion structure. Then Use table-driven tests with meaningful case names and t.Run subtests. A map is one possible table structure. Use -run=Parent/Subtest to focus diagnosis. Tables should contain related cases with shared assertions, not force unrelated behavior into complex branching. Because Reduces boilerplate and makes new cases and shared improvements easier.

- **G179** When parallel table subtests capture iteration variables. Then Check the effective module/file language version. Go 1.22+ gives fresh per-iteration variables when the loop declares them with :=, including three-clause loops. Assignment with = still reuses existing variables. In older language modes or with explicitly shared variables, copy the value or pass it as an argument. Distinct value copies differ from pointers to original slice elements obtained by index. Fresh loop variables do not determine goroutine or parallel-subtest execution order. Because Parallel subtests resume after the parent releases them. Shared loop variables can make several cases test the same value.

- **G180** When testing asynchronous completion. Then Synchronize with an observable event or channel instead of sleeping a guessed duration. Bound waits to prevent hung tests. A test-friendly design should expose useful completion behavior. Because Scheduling and machine load make fixed sleeps flaky.

- **G181** When synchronization is truly unavailable in an asynchronous test. Then Use a bounded eventual assertion with a short retry interval. Reconsider design first. Polling is still a fallback rather than a deterministic guarantee. Because Can finish as soon as the condition succeeds and is less brittle than one long sleep.

- **G182** When testing behavior based on current time. Then Inject a clock function or small clock interface and supply deterministic times in tests. Keep the dependency on the instance rather than a mutable global so tests remain isolated and parallelizable. In clock-dependent code, avoid mutating state under RLock and handle the all-expired boundary correctly. Because Direct time.Now calls make results depend on execution timing.

- **G183** When the API can naturally accept a time boundary. Then Let callers supply the current time or cutoff time. Simpler but less general than a clock dependency. Useful for external-package tests that cannot set private fields. A caller-supplied cutoff shifts time-selection responsibility into the API contract. Because This makes tests deterministic without a clock stub.

- **G184** When testing HTTP handler behavior. Then Use httptest.NewRequest and NewRecorder and assert headers, body, and status. This does not test transport. Because Direct calls are fast and capture handler behavior.

- **G185** When testing an HTTP client. Then Use httptest.NewServer with a controlled handler, its URL, and cleanup. Use NewTLSServer for TLS and NewUnstartedServer when setup must precede startup. Assert outgoing requests as well as response parsing when those requests are part of the client contract. Because Exercises real local HTTP requests without an external service or container.

- **G186** When implementing a custom reader. Then Validate the reader contract with iotest.TestReader. Supply the actual expected output. Exercise the reader contract beyond one successful read, including supported optional interfaces. Because Tests returned byte counts, delivered data, and optional reader capabilities.

- **G187** When testing I/O consumers against partial reads and failures. Then Use iotest.ErrReader, HalfReader, OneByteReader, TimeoutReader, or TruncateWriter as appropriate. Retry only when the operation contract allows it. ErrReader, HalfReader, OneByteReader, TimeoutReader and TruncateWriter cover different failure/partial-I/O behaviors. A retry-all-errors read loop is illustrative, not a universal contract. Because Simulates important I/O behaviors without bespoke fakes.

- **G188** When benchmark setup is outside the work being measured. Then With traditional b.N loops, ResetTimer after one-time setup and StopTimer/StartTimer around unrelated per-iteration work. On Go 1.24+, consider the prescribed for b.Loop() form, which excludes surrounding setup/cleanup and runs them once. Untimed setup still consumes wall-clock time, so select benchtime deliberately. Because Otherwise reported time and allocation costs include unrelated work.

- **G189** When interpreting small benchmark differences. Then Repeat runs, inspect variation with benchstat, and use adequate benchtime on a quiet representative machine. Conclusions apply to the measured compiler, architecture, and workload. Production can differ. Power state, code/data alignment and cache layout can influence tiny differences. perflock is an optional way to limit competing machine activity. Because Thermal, scheduling, cache, and other effects can reverse apparent results.

- **G190** When a benchmark calls a pure function whose result is unused. Then Make results observable in traditional b.N benchmarks, for example keep a local result and publish it to a sink after the loop to limit sink overhead. Go 1.24+ B.Loop protects call inputs/results in its prescribed loop form. Go 1.24-1.25 inhibited inlining there, while Go 1.26 restores normal inlining and protects assigned variables too. Compare compiler versions explicitly rather than disabling valid optimization. Because Inlining and dead-code elimination can turn the measurement into an empty loop.

- **G191** When repeated benchmark iterations reuse input data. Then Match warm versus fresh input and cache state to the intended use, recreating data when needed. Recreating data is not universally correct if production intentionally reuses it. Keep setup outside measured time. Because Repeated observation can warm caches and produce misleading results for fresh-input workloads.

- **G192** When identifying untested behavior. Then Generate a coverage profile and inspect it, including -coverpkg when tests cover other packages. Coverage percentage does not establish assertion quality or correctness. Do not chase 100% blindly. Inspect the coverage HTML report for missing paths. Coverage counts execution, not useful assertions. Because Default reporting can miss coverage exercised from another package.

- **G193** When tests should constrain public behavior rather than implementation. Then Use an external package_name_test package. Same-package tests remain useful where internal behavior needs inspection. Because Prevents direct access to private details and keeps tests stable during internal refactoring.

- **G194** When repeated test setup can fail. Then Pass *testing.T to test helpers and fail the test there when setup cannot succeed. Keep this behavior in testing helpers, not production APIs. Because Removes repeated production-style error plumbing from each test.

- **G195** When test helpers acquire resources. Then Register teardown with t.Cleanup or defer in the owning test. Cleanup callbacks run in reverse registration order. Because Ensures lifecycle responsibility is not forgotten by callers.

- **G196** When a package needs shared expensive environment setup. Then Use TestMain to set up, run m.Run, tear down, and preserve the result code. Run teardown before os.Exit, which does not run defers. Shared package infrastructure must not compromise individual test isolation. Because Avoids repeated setup while guaranteeing orderly package-level teardown.

- **G197** When optimizing a codebase. Then Prioritize correctness and clarity, then optimize measured paths with a concrete benefit. Performance work is justified by actual user, capacity, or cost needs. Prefer readability to speculative speed. Benchmark representative changes because compiler, hardware and data behavior can defeat intuition. Because Complexity has a maintenance cost and guessed optimization may solve no real problem.

- **G198** When designing interface granularity. Then Keep interfaces small and compose them when a larger combined behavior is required. Choose sufficient granularity for the real behavior, not minimalism for its own sake. Compose small interfaces when combined behavior is needed. Granularity should match actual meaning, not an arbitrary one-method rule. Because Fewer required methods increase reuse and composability.

- **G199** When optimizing data-heavy loops. Then Arrange access to reuse nearby data and exploit temporal and spatial locality. Cache sizes and line widths depend on hardware. Counted operations alone do not predict running time. Machine cache sizes, latency ratios and typical 64-byte lines are illustrative. Consider the machine model only for measured bottlenecks. Because CPUs fetch cache lines, so useful adjacent data can amortize memory access cost.

- **G200** When hot code scans only a subset of record fields. Then Consider a struct of slices instead of a slice of structs for the hot fields. This is an access-pattern tradeoff, not a universal preferred representation. Total bytes may stay unchanged while useful fields per cache line increase. Whole-record operations can favor the opposite representation. Because More useful values fit in each fetched cache line.

- **G201** When choosing data structures for hot traversal. Then Prefer predictable contiguous or constant-stride access when suitable. Semantics and other operation costs may require linked structures. Measure target hardware. Even contiguous allocation of a linked structure leaves dependent pointer loads. Do not assume that non-unit strides are never prefetched. Because CPUs can prefetch predictable accesses more effectively than pointer chasing.

- **G202** When a hot strided access pattern has unexpected cache misses. Then Investigate cache-set conflicts and avoid critical strides when measurements justify a layout change. Architecture-specific optimization. Verify bit/byte arithmetic against the target cache geometry. Input reuse and the actual cache geometry determine whether a critical stride matters. Because Addresses mapping repeatedly to one cache set evict each other.

- **G203** When independent concurrent writers update nearby fields. Then Check for false sharing and consider padding or independent local results passed through channels. Data-race freedom does not eliminate false sharing. Padding size depends on cache architecture and costs memory. The sample 56-byte padding assumes an 8-byte field and 64-byte cache line. Do not hardcode that geometry for all targets. Because Coherence works at cache-line granularity, so unrelated fields can invalidate each other's caches.

- **G204** When a measured CPU-bound loop has dependent operations. Then Inspect generated code and consider equivalent transformations that reduce data dependencies. Maintain correctness and clarity. Compiler and processor changes can invalidate a micro-optimization. A temporary pre-update value can expose independence, but preserve the branch semantics as well as arithmetic results. Because Independent instruction paths allow instruction-level parallelism.

- **G205** When many copies of a struct consume substantial memory. Then Inspect field layout and consider grouping fields by decreasing alignment/size to reduce padding. Do not assume one alignment table applies universally. Alignment varies by type/architecture and layout changes can have API implications. Treat descending size/alignment as a layout heuristic. Verify the actual target layout before accepting byte/bit or word-size claims. Do not sacrifice a clear public API merely to remove padding without a measured benefit. Because Smaller structs reduce memory traffic, GC pressure, and cache-line use.

- **G206** When choosing values versus pointers for performance. Then Choose semantics first and benchmark allocation and copy costs before replacing values with pointers. A pointer is not automatically faster. Stack and heap behavior depends on escape analysis and inlining. Because Pointers can force heap allocation and GC work while value copies can be cheap.

- **G207** When measuring allocation-sensitive work. Then Use benchmark allocation reporting to inspect bytes and allocations per operation. ReportAllocs measures heap allocations, not ordinary stack allocations. Heap allocation adds allocator and GC work that ordinary stack-frame reuse does not incur. Because Time alone can hide heap pressure.

- **G208** When a change may make objects escape. Then Inspect compiler decisions with go build -gcflags '-m=2'. Sharing-up/down rules are heuristics. Compiler behavior evolves. Sending references through channels, appending and variable or large allocations are contextual examples, not an exhaustive escape law. Because Escape analysis is contextual, and returning references, sending references, dynamic sizes, or large objects may escape.

- **G209** When a hot API produces buffers repeatedly. Then Consider accepting caller-provided storage instead of always allocating and returning it. Passing storage down does not guarantee stack allocation. Check escape analysis. Because Callers can reuse storage and avoid forcing a fresh escaping allocation.

- **G210** When using byte data to look up string-keyed maps. Then Consider direct m[string(bytes)] lookup and verify compiler allocation behavior. Optimization details change by compiler version. Do not generalize to map insertion or retained strings. A separately stored conversion may compile differently from direct lookup. Do not extrapolate the optimization to insertion, retained strings or unsafe mutation. Because The compiler can avoid a temporary conversion allocation in this expression.

- **G211** When a profile shows repeated allocations of interchangeable temporary objects. Then Consider sync.Pool with a factory, reset acquired objects, and return them after use. A pool is not a durable cache or a bounded resource pool. Objects may disappear and concurrent pool safety does not make checked-out objects safe to share. Do not access an object after returning it to the pool. A creation path must handle empty pools. Historical GC-removal timing is not a retention guarantee. Because Reuse can lower amortized allocations and GC pressure.

- **G212** When designing pooled buffer ownership. Then Ensure the active slice length and state are reset and subsequent writes are reflected in the object actually used and returned. Reset logical slice length and all other reusable state. Return ownership only after the active operation finishes. Because Stale state or a lost updated slice header defeats correctness despite lower allocations.

- **G213** When a frequently used function has a tiny fast path and complex slow path. Then Consider extracting the slow path so the fast wrapper can inline, then verify compiler output and benchmarks. Inlining budgets and compiler decisions are version-dependent. Avoid refactoring without evidence. Use -gcflags=-m=2 diagnostics to verify inlining decisions. Fast-path inlining may enable escape and constant optimizations beyond removing a call. Because Inlining removes call overhead and can enable further escape and constant optimizations.

- **G214** When diagnosing performance rather than guessing. Then Collect the relevant pprof profile and inspect hot functions, call chains, and source lines. Choose sampling rates deliberately. Profile overhead and representative load matter. Because Profiling identifies actual CPU, allocation, goroutine, and contention costs.

- **G215** When CPU time is the suspected bottleneck. Then Use a bounded CPU profile, including -cpuprofile for benchmarks, and inspect call graph, top, or flame graph views. Sampling is statistical, not exact per-call timing. Labels can separate callers sharing a function. A sampling interval is not a hard minimum function duration visible in a CPU profile. Shorter intervals increase overhead. Because Locates expensive paths and suggests allocation, contention, or I/O-buffering work.

- **G216** When analyzing memory cost. Then Distinguish cumulative allocation count/bytes from in-use object count/bytes. Profiles concern heap allocations and are sampled. The profile keys are alloc_objects, alloc_space, inuse_objects and inuse_space. Heap sampling trades precision against overhead and does not count stack storage. Because High allocation churn and retained memory are different problems.

- **G217** When investigating a suspected memory leak. Then Compare heap profiles over time after GC and look for sustained retained growth. A single increase can reflect an in-flight request. Repeat under comparable workloads. Forced GC perturbs execution. Compare meaningful intervals and comparable load, and state the direction of the diff-base comparison. Because A pre-GC spike may merely be collectible garbage.

- **G218** When investigating leaked or stuck goroutines. Then Inspect goroutine profiles or a full goroutine stack dump. Use debug=2 for a full textual dump and compare lifecycle expectations. Inspect wait states, durations and creation sites against expected lifecycle. One blocked-stack snapshot is a diagnostic lead, not proof of a leak. Because Stacks reveal where goroutines remain active or blocked.

- **G219** When synchronization appears to limit throughput. Then Enable SetBlockProfileRate or SetMutexProfileFraction deliberately before the interval of interest. Use block profiles for supported synchronization waits rather than assuming they cover arbitrary network/filesystem I/O. Go 1.22+ mutex samples sum goroutine delay: 100 goroutines waiting 10 ms can contribute 1 second. Go 1.25 improves runtime-lock attribution. Rates affect overhead and CPU samples alone may hide waiting. Because Attributes waits and contention to relevant code.

- **G220** When collecting multiple diagnostic signals. Then Collect intrusive diagnostic profiles separately when simultaneous instrumentation could distort measurements. Default heap data need not be disabled merely because another diagnostic is active. The concern is observer interference from simultaneous expensive instrumentation. Because Observation can perturb the behavior being measured.

- **G221** When understanding scheduling, GC pauses, or poor parallelism. Then Capture an execution trace and inspect goroutine activity across processors. Do not equate every blank interval with one cause without investigation. Many tiny execution segments and orchestration gaps can suggest scheduling overhead. Trace overhead and representative workload still matter. Because Trace events reveal scheduling overhead and runtime pauses that aggregate profiles obscure.

- **G222** When trace data needs application-level meaning. Then Annotate tasks and regions with runtime/trace and end tasks appropriately. Instrumentation adds work and should target useful boundaries. Execution trace is event-based while CPU profiling is sampled. Their evidence is complementary. Because Connects runtime events to operations and duration distributions.

- **G223** When GC cost appears significant. Then Measure GC behavior, using gctrace or diagnostics, before tuning. Runtime internals and defaults are version-sensitive. GODEBUG=gctrace=1 exposes collection frequency and costs. Live references, allocation rate, concurrent work and brief stop-the-world phases matter. Historical fixed CPU percentages and pause figures are not runtime guarantees. Because Heap size, allocation rate, and collection effort interact.

- **G224** When balancing memory use against GC CPU and latency. Then Tune GOGC only under representative load. Higher values generally allow more heap growth and fewer collections, with memory and per-cycle cost tradeoffs. Go 1.19+ GOMEMLIMIT provides a separate soft Go-managed-memory limit even with GOGC=off. Leave headroom for non-Go allocations and OS memory. Near the live-heap size the runtime can exceed the limit to make progress. Because More growth between collections reduces frequency but increases memory and potentially cycle cost.

- **G225** When memory remains after a temporary allocation peak. Then Allow the scavenger to return unused memory, and consider debug.FreeOSMemory only for a demonstrated need. Manual collection/scavenging has costs and is not routine application logic. Distinguish retained live objects, reusable heap space and memory actually returned to the OS. Forced release does not fix unwanted live references. Because Heap capacity and OS-reported memory do not immediately track live objects.

- **G226** When evaluating retained ballast for allocation bursts. Then Prefer measuring GOGC and, from Go 1.19, GOMEMLIMIT before considering retained ballast. Ballast is a historical exceptional technique, not a default. Its address-space use, physical pages touched, OS lazy allocation and container accounting need dedicated validation. A 1 GB ballast size is not reusable configuration. Because Increasing the minimum live heap can reduce burst-triggered GC frequency.

- **G227** When deploying Go under container CPU quotas. Then Inspect runtime.GOMAXPROCS(0), CPU affinity/quota and program GODEBUG settings. On Go 1.25+, Linux quota awareness and periodic updates on all platforms default on for program compatibility defaults >=1.25, and off for defaults <=1.24. These defaults follow the active workspace or work module, then godebug and main-package //go:debug overrides. Per-file language gates do not select them. Inspect go list -f '{{.DefaultGODEBUG}}' for the main package and runtime GODEBUG environment overrides. A positive GOMAXPROCS environment override or value-setting runtime.GOMAXPROCS call disables automatic updates. runtime.SetDefaultGOMAXPROCS (Go 1.25+) restores managed defaults. Quotas differ from Kubernetes CPU requests, and matching them does not guarantee zero throttling. Measure throttling and tail latency before changing settings. Because Host-core-based concurrency can exhaust a quota early and cause pauses.

- **G228** When the runtime does not derive execution capacity from the container quota. Then First inspect actual runtime and module behavior using the container rule. If quota-aware defaults are unavailable or intentionally disabled, consider an explicit quota-aware adjustment such as automaxprocs. Measure its effect and avoid an unnecessary override of working Go 1.25+ managed defaults. Because Bounds simultaneous execution to the container's intended capacity.

- **G229** When initializing static configuration. Then Consider init for non-failing static setup that does not compromise tests. Assess failure and global-state behavior, init is not universally forbidden. Registration or static configuration can fit init if it introduces no failure, mutable-global or test-isolation problem. Because Some registration and configuration side effects fit package initialization.

- **G230** When using a builder with chaining. Then When chained setters cannot return validation errors, perform validation and default resolution explicitly in Build. Builder patterns are valid, but deferred validation and extra construction steps can complicate clients. Builders are valid alternatives but can make default construction and precise per-option errors less convenient. Because Chained setters returning the builder cannot also provide ordinary Go error handling.

- **G231** When choosing pointer collections. Then Use pointers when sharing is intended, pointers already exist, or large frequently mutated values justify avoiding copies. Do not choose pointers automatically, clarify who shares the pointee. Pointer elements can worsen locality and make ownership/sharing less obvious. Avoid pointers merely by habit. Because Pointer storage changes semantics and mutation cost.

- **G232** When carrying request metadata across API boundaries. Then Use context values for cross-cutting information such as correlation IDs or middleware metadata. Mutable values require their own synchronization, context concurrency safety does not protect pointees. Standard context concurrency safety does not synchronize mutable values or pointees stored in that context. Because Related operations can share metadata without invasive plumbing.

- **G233** When choosing a root context. Then Use Background for a deliberate root and TODO when the correct context is unresolved. Because TODO documents incomplete context propagation.

- **G234** When the same function serves several workloads. Then Attach pprof labels where differentiation matters. Label selection should support the diagnostic question. Because Separates costs by logical caller or workload.

- **G235** When enabling production diagnostics. Then Consider net/http/pprof or programmatic/benchmark profile collection with awareness of sampling cost. Profiles such as CPU are collected for a chosen interval. A diagnostic mechanism does not establish a production endpoint-exposure or security policy. Because Provides actionable diagnostics without continuously enabling every expensive profile.

- **G236** When cPU profiles show allocation, synchronization or syscall overhead. Then Reduce unnecessary allocations, investigate contention, or consider I/O buffering based on the observed hotspot. These are diagnostic hypotheses, not automatic fixes. Because Targets the runtime cost actually dominating execution.

- **G237** When built-in profiles do not cover a resource of interest. Then Consider a custom pprof.Profile. Historical reports that threadcreate was broken do not establish current tool behavior. Because Extends diagnostics to application-specific accounting.

- **G238** When applying Go development guidance. Then Retain the specific context and alternatives instead of treating every recommendation as a dogmatic rule. This guidance assumes existing Go knowledge and concentrates on the core language and standard library. Because Solutions depend on context.

- **G239** When a receiver is large. Then Consider a pointer receiver and benchmark the copy-versus-pointer tradeoff. There is no universal size cutoff. Semantics take priority over speculative optimization. A preference for pointers when otherwise undecided is only a heuristic. Receiver semantics and measurement govern the choice. Because Large copies can be costly.

- **G240** When zero is a valid explicit option. Then Represent absence separately from zero, for example with a pointer in configuration. Pointer configuration adds caller friction. A pointer field is one way to distinguish omission from explicit zero, but it adds caller friction. Apply domain-specific invalid-value validation separately. Because A missing value and an explicitly supplied zero otherwise become indistinguishable.

- **G241** When building, reviewing or upgrading a Go module. Then Record the supported minimum Go version, go.mod/go.work directives, per-file build constraints, actual selected toolchain, GOTOOLCHAIN and target platforms. From Go 1.21 the go directive is a strict minimum and toolchain selection may download another compiler. A newer compiler alone does not enable newer language semantics in an older module. Validate the minimum with an actual baseline toolchain when compatibility is claimed. Because Language permission, library availability and runtime compatibility defaults are separate inputs.

- **G242** When upgrading a runtime or changing GODEBUG settings. Then Inspect relevant release entries for all crossed versions and their patch, module and experiment gates. On Go 1.27, asynctimerchan, gotypesalias, tlsunsafeekm, tlsrsakex, tls3des, tls10server and x509keypairleaf are removed. Removed keys in module/source declarations only accept their final values. Test behavior instead of prescribing a removed workaround. Because Compatibility switches can expire and source-era advice can become invalid.

- **G243** When modernizing Go source or verification tooling. Then Run the target toolchain's go fix and vet checks as appropriate, then review the diff and relevant behavioral tests. Go 1.26 rebuilds go fix around modernizers, and Go 1.27 changes modernizer names and defaults stdversion into go test. Account for output/JSON changes in tool consumers. Because Automated migration and diagnostics help locate changes but do not establish application semantics.

- **G244** When installing tools or updating module dependencies. Then In module mode on Go 1.18+, use go install path@version for executables and go get for dependencies. Use deliberate tidy/download updates, and review go.mod/go.sum changes. Go 1.24+ tool directives and go tool can track executable dependencies. A go1.27+ module may have require blocks consolidated by tidy. Because Tool installation, dependency changes and reproducible build inputs have different ownership.

- **G245** When working in a multi-module checkout. Then Inspect go env GOWORK and the discovered go.work before interpreting dependency resolution. Go 1.18 workspaces select multiple main modules. Go 1.22 adds workspace vendor trees. Verify intended module-only behavior with GOWORK=off when publishing or testing a module independently. Because An enclosing workspace or its vendor tree can hide a missing module requirement.

- **G246** When building for different operating systems, CPU levels or cgo environments. Then Consult the platform entries for the selected release and verify GOOS, GOARCH, architecture feature levels, OS minimums, C compiler/linker and external library ABI. Higher GOAMD64/GOARM64/GORISCV64 settings constrain deployment hardware. Go 1.27 requires macOS 13+, and linux/ppc64 uses ELFv2 with compatible libc/libraries for cgo. Because A successful host build does not prove deployment compatibility.

- **G247** When using experimental Go features. Then Record the exact toolchain and GOEXPERIMENT settings and isolate unstable APIs. Go 1.24 synctest.Run and Go 1.25 JSON v2 are historical experiments, not their later stable APIs. Go 1.27 simd/archsimd and runtime/secret remain experimental. Review later release entries before carrying experiment switches forward. Because An experiment is outside the ordinary stable API contract, even when a later feature shares its name.

- **G248** When introducing generic aliases or newer expression syntax. Then Require Go 1.24 language support for stable generic aliases, including cross-package use. Require Go 1.26 for new(expression) and self-referential generic constraints. Go 1.23 aliases are only an intra-package experiment. Keep older baselines using supported forms rather than relying on the installed compiler alone. Because Syntax and type-system capabilities follow effective language versions.

- **G249** When implementing collection comparisons, copies, searches or sorting. Then Check stable slices, maps and cmp on Go 1.21+ before writing equivalent loops. Keep equality semantics, nil behavior, shallow-copy ownership and alias effects explicit. Earlier x/exp packages are separately versioned and do not carry the standard-library compatibility promise. Because Standard helpers reduce duplication when their contracts match the needed behavior.

- **G250** When using integer or function range and iterator helpers. Then Require Go 1.22 language support for integer range and Go 1.23 for stable function range. Match the allowed yield signature, stop producing when yield returns false, and preserve cancellation/resource ownership. iter plus slices/maps iterator helpers are Go 1.23 APIs. Go 1.24 strings/bytes sequence helpers can avoid intermediate collections but retain their underlying data. - **G251** When representing independently atomic shared state. Then Consider Go 1.19+ typed atomics, including atomic.Pointer[T], and retain sequentially consistent synchronization reasoning. Typed Int64/Uint64 supply needed 64-bit alignment on 32-bit targets. Go 1.23 adds atomic And/Or. Keep compound invariants under a suitable lock or protocol. - **G252** When callers need a cancellation reason beyond canceled or deadline exceeded. - **G253** When combining or inspecting multiple failures. Then On Go 1.20+, use errors.Join or multiple %w operands when callers should inspect all causes. - **G254** When code needs reproducible noncryptographic randomness, including production simulations, sampling, replay or tests. Then Own a local seeded generator instead of relying on package-global state. math/rand autoseeds from Go 1.20 and top-level Seed becomes a no-op by default in Go 1.24. math/rand/v2 is available from Go 1.22 with different sources and names. A fixed seed does not control goroutine scheduling. Because Global defaults and algorithms change across versions and shared state breaks isolation.

- **G255** When testing input parsers or transformations with broad input domains. Then Use Go 1.18+ testing.F with a small meaningful seed corpus and properties about valid/invalid inputs. Set fuzz time/minimization budgets, retain reproducing failures, and manage GOCACHE/fuzz disk usage with go clean -fuzzcache when appropriate. Because Fuzzing explores cases beyond examples, but cache growth and execution budgets need ownership.

- **G256** When integration execution needs coverage evidence. Then On Go 1.20+, build with -cover, set GOCOVERDIR for executions, and inspect application coverage alongside unit coverage. For long-running processes use runtime/coverage when normal exit cannot write the needed evidence. Keep coverage separate from assertion quality. - **G257** When testing concurrent time-based behavior on Go 1.25+. Then Consider testing/synctest.Test and Wait for a fake-time bubble whose clock advances when goroutines are durably blocked. Arrange cleanup and join workers explicitly rather than assuming test return proves completion. Because Process-wide mutations can contaminate other tests, while resource cleanup has ordering requirements.

- **G259** When choosing omission rules for JSON fields. Then Distinguish omitted values from explicit zero and distinguish omitzero from omitempty.
